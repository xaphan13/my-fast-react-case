# 12. Связка FastAPI + React: способы организации фронтенда

Документ отвечает на вопрос: «почему сайт работает, даже если React не запущен —
только FastAPI, страницы отображаются; зачем тогда `npm run dev`?» — и шире:
какие вообще бывают способы организации связки бэкенда на FastAPI и фронтенда на
React/JS. Полезно читать вместе с [`docs/11_md_articles.md`](11_md_articles.md)
(там — конкретная архитектура блога этого проекта).

## 1. Ключевая идея: React живёт в браузере, а не на сервере

React — это **библиотека для браузера**. Всё, что делает «фронтенд-сервер»
(Vite dev server, Node), — это инструменты *подготовки* того JavaScript, который
браузер скачает и исполнит у себя. Когда подготовка закончена (сборка), серверная
часть фронтенда больше не нужна: остаётся просто набор статических файлов.

FastAPI в этой картине умеет две независимые роли:

1. **API** — отдаёт JSON по `/api/...` (вся логика, БД, сессии);
2. **статика/SPA-хост** — раздаёт собранные файлы фронтенда и `index.html`.

Отсюда главный вывод: «запущенный фронтенд» — это не условие работы сайта, а
условие **удобной разработки**.

## 2. Способы организации связки (от простого к сложному)

### Способ A. Статическая сборка + SPA-хостинг в FastAPI (этот проект)

```
Разработка:  npm run dev (Vite :5173, HMR)  ──прокси──▶  FastAPI :8000 (API)
Эксплуатация: npm run build → frontend/dist/  ◀──раздаёт── FastAPI :8000
                (/assets mount + catch-all на index.html)
```

- Vite компилирует `frontend/src/` (TypeScript, TSX, Tailwind) в бандлы
  `dist/assets/*.js|css` + `dist/index.html`.
- FastAPI: mount `/assets` → файлы бандлов; catch-all `/{full_path:path}` →
  `index.html` для всех не-`/api` путей (клиентский роутинг React Router);
  для `/api*` — 404 JSON.
- Браузер один раз скачивает бандлы, React работает на клиенте, данные тянет
  `fetch('/api/...')` с того же origin — **никакого CORS**, никаких отдельных
  доменов.

**Плюсы:** один сервер, один порт, нулевая инфраструктура вокруг фронтенда;
простой деплой (один процесс FastAPI + каталог `dist/`).
**Минусы:** после правки `src/` обязательно `npm run build`, иначе браузер
получает старый бандл (`dist/` в `.gitignore` — на новой машине пересобрать);
для разработки нужен второй процесс (dev-сервер).

**Почему страницы работают без «запущенного фронтенда»:** FastAPI отдаёт уже
скомпилированный бандл. React при этом полностью работоспособен — он исполняется
в браузере, а не на сервере. `npm run dev` здесь — только инструмент разработчика:
собирает исходники в памяти, обновляет страницу при сохранении (HMR), а запросы
`/api` и `/static` проксирует на FastAPI (`frontend/vite.config.ts`).

### Способ B. Раздельные домены: Vite/Nginx отдельно, FastAPI — только API

```
Браузер ──▶ https://app.example.com (Nginx/Vercel/Netlify — статику dist/)
        ──▶ https://api.example.com (FastAPI — только JSON API)
```

- Фронтенд собирается тем же `npm run build`, но раздаётся не FastAPI, а
  специализированным статик-хостом (Nginx, CDN, Vercel/Netlify/Cloudflare Pages).
- FastAPI не знает про фронтенд вообще: только `/api`.

**Плюсы:** масштабирование частей независимо; API переиспользуется другими
клиентами (мобильное приложение, интеграции); CDN для статики.
**Минусы:** **CORS** — обязательная настройка `CORSMiddleware` на FastAPI
(`allow_origins=[...]`) — браузер блокирует междоменные запросы с credentials
по умолчанию; два домена/сертификата/деплоя; cookie-сессии через домены
требуют `SameSite=None; Secure` и общих доменов.

В этом проекте такого режима нет, но подготовка к нему есть: nginx-стек
`nginx_pg_admin.yml` — прод-подобная схема, где nginx терминирует TLS и умеет
проксировать приложение.

### Способ C. SSR-фреймворк (Next.js/Remix) + FastAPI API

```
Браузер ──▶ Next.js (Node-сервер, рендерит HTML на сервере) ──fetch──▶ FastAPI API
```

- React-компоненты выполняются **на сервере** (Node): HTML приходит в браузер
  уже с контентом; hydration достраивает интерактив.
- FastAPI — чистый API-бэкенд; Node — обязателен в рантайме (не только в сборке).

**Плюсы:** SEO (в HTML сразу контент), быстрая первая отрисовка, метатеги
социальных сетей.
**Минусы:** два рантайма в эксплуатации (Node + Python); сложность (двойной
рендер, состояние hydration); для «личного блога с API-доступом» обычно избыточно.

### Способ D. Серверные шаблоны без SPA (предыдущая версия этого блога)

```
Браузер ──▶ FastAPI: Jinja2-шаблоны + фрагменты HTML (+ htmx/Alpine.js по вкусу)
```

- Никакого React-бандла: FastAPI рендерит HTML серверно (Jinja2), браузер —
  «тонкий» клиент; интерактивность добавляется точечно (htmx, Alpine.js, немного
  ванильного JS).
- Исторический путь этого проекта отражает эволюцию веб-стеков:
  серверные шаблоны (Jinja/htmx) → SPA на React. Подробности — в заданиях
  `tasks/NNN-*/`.

**Плюсы:** минимум движущихся частей, никакого Node, SEO из коробки.
**Минусы:** интерактивность даётся дороже; состояние на клиенте держать
неудобно; UI-компонентность слабее.

### Способ E. Гибрид: FastAPI отдаёт HTML-каркас, React — «островки»

- FastAPI рендерит основную страницу (Jinja2), в конкретные места монтируются
  React-виджеты (`createRoot(el).render(...)` на несколько корней), каждый тянет
  свои данные из API. Подходит, когда интерактив нужен локально (корзина,
  комментарии), а остальное — статика. Иногда это называют
  islands-архитектурой (в чистом виде — Astro, но идею повторяют вручную).

**Плюсы:** точечная интерактивность без SPA-роутинга.
**Минусы:** два мира в одном проекте; общий стейт между «островками» — боль.

## 3. Сравнительная таблица

| Критерий | A: SPA в FastAPI (проект) | B: раздельные домены | C: Next.js SSR | D: Jinja2 | E: островки |
|---|---|---|---|---|---|
| Node в рантайме | нет | нет | **да** | нет | нет |
| Нужен `npm run dev` для работы | нет (только для разработки) | нет | для разработки | — | частично |
| CORS-настройка | не нужна | **обязательна** | не нужна (прокси) | не нужна | не нужна |
| SEO | слабое (пустой index.html) | слабое | **отличное** | **отличное** | хорошее |
| Число деплой-юнитов | 1 | 2 | 2 | 1 | 1 |
| Сложность | низкая | средняя | высокая | низкая | средняя |
| Где живёт состояние UI | браузер | браузер | сервер+браузер | сервер | смешанное |

## 4. Как это устроено конкретно в этом проекте (кратко)

- **Эксплуатация** — способ A: `frontend/dist/` собирается `npm run build`,
  [`setup_frontend.py`](../fastapi-application/md_articles/setup_frontend.py) монтирует `/assets`
  и отдаёт `dist/index.html` через catch-all; `/api/blog/*` — JSON API. Один
  процесс FastAPI обслуживает всё.
- **Разработка** — временно способ B-подобный: Vite на `:5173` отдаёт исходники
  с HMR и проксирует `/api` и `/static` на `:8000` (`vite.config.ts`). Оба
  процесса нужны **только пока правишь фронтенд**; браузер в это время ходит на
  5173.
- **Грабля режима A:** правки `frontend/src/` не видны пользователю до
  пересборки — после каждой задачи фронтенда обязательна контрольная сборка.

Подробности про код в `setup_frontend.py` — почему именно три шага, почему
catch-all добавляется в `router.routes` руками, как ведёт себя dev-режим без
`dist/`, пошаговая трассировка запросов — в
[`docs/13_frontend_spa_module.md`](13_frontend_spa_module.md).

## 5. Как выбрать

- **Личный проект / внутренний сервис / JSON-first сайт** → способ A (как здесь):
  минимум инфраструктуры, API и UI в одном деплое.
- **Публичный продукт с отдельной фронтенд-командой / CDN / мобильным клиентом** →
  способ B (+ CORS, токены-сессии или cookie с общим доменом).
- **SEO-критичный контент, соцсети, маркетинг** → способ C (или D/гибрид).
- **Маленький интерактив поверх серверных страниц** → D или E.

## 6. Частые вопросы

**«Зачем `npm run dev`, если всё работает без него?»** — `dev` не делает сайт
работающим, он делает разработку быстрой: HMR (правка → мгновенное обновление
без пересборки), осмысленные ошибки на исходниках TS/TSX, прокси API. Без него
каждая правка — цикл `npm run build` + F5.

**«FastAPI отдаёт React?»** — нет, FastAPI отдаёт **файлы** (JS/CSS/HTML).
React исполняется в браузере пользователя. Убери Node после сборки — сайт
продолжает работать.

**«Почему нет CORS-ошибок?»** — API и бандлы живут на одном origin
(`127.0.0.1:8000`), браузер не видит междоменных запросов. Появится отдельный
домен для API — понадобится `CORSMiddleware` с `allow_origins`,
`allow_credentials=True` и cookie-политикой `SameSite=None; Secure`.

**«SPA catch-all зачем?»** — React Router делает роутинг на клиенте
(`/section/Rust`, `/art/Max/123`). При прямом заходе на такой URL сервер должен
вернуть `index.html` (роутер сам разберётся), а не 404 — для этого catch-all
`/{full_path:path}`; `/api*` при этом перехватывается раньше и честно отвечает
404 JSON для неизвестных API-путей.
