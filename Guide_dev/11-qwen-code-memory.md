# 11. Память Qwen Code: что где хранится и как переносить

> Цикл «FastAPI + React». Предыдущая: [10. URL-flow](10-url-flow.md)

Эта статья — не про FastAPI и не про React. Она про то, как устроена
**память ассистента Qwen Code**, с которым вы ведёте разработку: что он
помнит между сессиями, где это лежит на диске, и как перенести
накопленные правила на другой компьютер.

Если коротко: память — это набор markdown-файлов в вашей домашней
директории `~/.qwen/`. Не в проекте, не в git-репозитории (если вы сами
туда не положите). Плюс автоматически загружаемый индекс `MEMORY.md`, по
которому ассистент в начале каждой сессии понимает, какие правила
применять.

## 0. Зачем вообще это знать

Три практических повода:

1. **Перенести накопленные правила на новую машину.** За полгода работы
   с ассистентом у вас в памяти оседают «не называй номер строки на
   глаз», «русский язык для документации», «сначала анализ, потом план,
   потом подтверждение» — перенести их простым копированием папки, а не
   пересказывать заново.
2. **Понять, почему ассистент в начале сессии ведёт себя «как будто знает
   проект».** Никакой магии: он прочитал `MEMORY.md` и подгрузил 3–10
   строк с правилами.
3. **Самому положить правило, если ассистент не догадался.** Формат
   файлов открытый — это просто markdown с frontmatter.

## 1. Где физически лежит память

Вся память — под `~/.qwen/`. Два корня:

```
~/.qwen/
├── memories/                          ← USER-память (кросс-проектная)
│   ├── MEMORY.md                      ← индекс, загружается в каждую сессию
│   ├── user/                          ← кто вы, ваш уровень, роль
│   ├── feedback/                      ← правила поведения «как делать»
│   ├── project/                       ← (обычно пусто в user-памяти)
│   └── reference/                     ← внешние ресурсы (Linear, Grafana, ...)
│
└── projects/                          ← PROJECT-память (по проекту на папку)
    └── <slug-рабочей-директории>/
        └── memory/
            ├── MEMORY.md              ← свой индекс
            ├── user/  feedback/  project/  reference/
```

`<slug>` в пути — это автоматически сгенерированное имя из рабочей
директории, например `-home-max-0-0-26-new-one-my-fast-react-case`. Когда
вы запускаете Qwen Code в другом репозитории — там будет **своя**
project-память, и ассистент не полезет в чужую.

### Что в каком каталоге

| Каталог | Что туда класть | Пример |
|---|---|---|
| `user/` | Профиль пользователя: роль, опыт, что знает, что нет | «Уверенно оперирует SPA, history-mode routing, fetch credentials» |
| `feedback/` | Правила «как делать» и «как не делать» — по сути корректировки поведения | «Перед ссылкой на строку N — `awk` её, не вспоминай» |
| `project/` (user) | Почти всегда пусто: проектные факты лучше класть в project-память проекта | — |
| `reference/` | Внешние ресурсы: Linear-доски, Grafana-дашборды, корпоративные вики | «Баги пайплайна в Linear-проекте INGEST» |

В **project-памяти** (внутри `projects/<slug>/memory/`):

| Каталог | Что туда класть |
|---|---|
| `project/` | Факты о проекте: baseline, архитектурные решения, текущая инициатива, кто что делает |
| `feedback/` | Правила, специфичные для этого проекта (например, «в этом репо не запускать pytest — нет тестов») |
| `user/` | Если роль пользователя разная в разных проектах — редкий случай |
| `reference/` | Ссылки на конкретные файлы/доски/документацию этого проекта |

**Главное разделение:** user-память кочует с вами между проектами,
project-память привязана к одному репозиторию. Если правило «русский
язык для документации» должно работать везде — оно в `~/.qwen/memories/feedback/`.
Если факт «baseline routes == 42 в ветке auth_refactor» — в
`projects/<slug>/memory/project/`.

## 2. Формат одного файла памяти

Один факт/правило = один файл. Не «пакет правил» в одном файле, не
«одна запись в большой index.md» — по файлу на запись, чтобы можно было
удалить одно правило, не трогая остальные.

Шаблон:

```markdown
---
name: Короткое название правила
description: Однострочный хук — по нему ассистент решает, релевантно ли правило
type: user | feedback | project | reference
---

Тело правила. Для feedback и project — структура такая:
первой строкой **само правило/факт**, затем **Why:** (обоснование — почему
так, какой случай к этому привёл), затем **How to apply:** (когда и как
применять, триггеры).
```

**Пример feedback-правила:**

```markdown
---
name: Проверять номера строк перед публикацией
description: Никогда не называть номер строки по памяти — перед ссылкой на «строку N» обязательно прогнать awk/sed/grep и сверить
type: feedback
---

Если в ответе пользователю упоминается конкретный номер строки в файле —
этот номер нужно проверить инструментом (awk/sed/grep), а не вспоминать.

**Why:** 2026-09-05 в задаче про helpers пользователь указал
`:40` и спросил про предупреждение IDE на этой строке. Я открыл файл
через `read_file`, но при формулировке ответа назвал строкой 40
функцию `_username_exists`, хотя реально она была на 46-й.
Пользователь поймал это мгновенно: «как так у нас строки то могут
отличаться — ты как файл то открываешь?».

**How to apply:**
- Перед любой ссылкой на `:NN` — прогнать `grep -n ... file` или
  `awk 'NR==NN' file` и убедиться, что там действительно то, о чём
  я говорю.
- «Оно наверняка там, я же только что читал» — не аргумент. Файлы
  большие, легко потерять место.
```

## 3. Индексы `MEMORY.md`

В каждой директории памяти лежит свой `MEMORY.md` — индекс файлов этой
директории. Формат — по одной строке на файл, ~150 символов максимум:

```markdown
- [Проверять номера строк перед публикацией](feedback/verify-line-numbers.md) — Никогда не называть номер строки по памяти — перед ссылкой на «строку…
- [Рабочий процесс: анализ, план, подтверждение, реализация](feedback/workflow-analysis-plan-approval.md) — Для изменений в коде пользователь предпочитает…
```

**`MEMORY.md` загружается в каждую сессию автоматически** — поэтому
длинные правила хранятся в файлах, а в индексе только однострочные
«хуки», по которым ассистент решает, нужно ли открывать файл.

## 4. Что НЕ сохранять в памяти

Частая ошибка — записывать в память то, что **и так видно в коде**:

- **Паттерны кода, конвенции, архитектура, файловые пути, структура
  проекта** — это всё восстанавливается чтением репозитория.
- **Git-история, кто что коммитил** — `git log` / `git blame` авторитетны.
- **Решения багов, рецепты фиксов** — фикс в коде, контекст в
  commit message.
- **Имена MCP-инструментов, схемы параметров** — живые определения
  инструментов авторитетны и могут меняться. Сохраняйте **только**
  workaround, владельца или escalation path.
- **Эфемерные детали задачи** — текущая работа, временные состояния,
  контекст разговора.

Исключения делаются, когда пользователь явно говорит «запомни это».

## 5. Как положить правило в память (ручной workflow)

Шаблон workflow, когда ассистент делает что-то **неправильно** (вы его
поправили):

1. Ассистент сохраняет правило в файл подходящего типа
   (`feedback/`, если это «как делать»).
2. Обновляет `MEMORY.md` — добавляет строку-указатель на новый файл.
3. Сообщает пользователю: «сохранил правило в `~/.qwen/memories/feedback/<slug>.md`».

Когда сохранять автоматически (ассистент решает сам):
- Пользователь явно попросил: «запомни это», «на будущее».
- Пользователь поправил поведение — это **валидация/коррекция**, которую
  имеет смысл запомнить.

Когда НЕ сохранять:
- Одноразовая правка без обобщения («тут опечатка» — не правило).
- Узкая проектная деталь — она идёт в project-память, а не user.

## 6. Перенос на новый компьютер

```
scp -r old-machine:~/.qwen/memories/  new-machine:~/.qwen/
scp -r old-machine:~/.qwen/projects/ new-machine:~/.qwen/
```

Всё. Ассистент на новой машине сразу подхватит правила из `MEMORY.md`.

**Не забывайте:** `output-language.md`, `QWEN.md`, `settings.json` —
тоже лежат в `~/.qwen/`, но это **настройки**, а не память. Их
переносите отдельно по необходимости.

## 7. Практические мелочи

- **Удаление устаревшего правила** — просто `rm` файла + убрать строку
  из `MEMORY.md`. Никаких миграций.
- **Конфликт правил** — два правила противоречат друг другу: более
  новое «главнее», но лучше явно переформулировать старый файл.
- **Память большая, ассистент медленный** — держите `MEMORY.md` коротким
  (≤50 строк на директорию); длинные правила — в файлах, ассистент
  открывает только релевантные.
- **Память видна только текущему пользователю ОС** — другие люди на той
  же машине не видят вашу память (это не git, не shared).

## 8. Чекпоинт самопроверки

- [ ] Знаете разницу между `~/.qwen/memories/` (user) и
      `~/.qwen/projects/<slug>/memory/` (project).
- [ ] Понимаете формат одного файла памяти (frontmatter + body).
- [ ] Не сохраняете в память то, что уже есть в коде.
- [ ] `MEMORY.md` в каждой директории — индекс, не сборник правил.
- [ ] Умеете перенести память на новую машину одной командой.
