# 11. Память Qwen Code: что где хранится и как переносить

> Цикл «FastAPI + React». Предыдущая: [10. URL от пользователя до бэкенда](10-url-flow.md)

Эта статья — не про FastAPI и не про React. Она про то, как устроена **память
ассистента Qwen Code**, с которым вы ведёте разработку: что он помнит между
сессиями, где это лежит на диске, и как перенести накопленные правила на
другой компьютер.

Если коротко: память — это набор markdown-файлов в вашей домашней директории
`~/.qwen/`. Не в проекте, не в git-репозитории (если вы сами туда не положите).
Плюс автоматически загружаемый индекс `MEMORY.md`, по которому ассистент в начале
каждой сессии понимает, какие правила применять.

## 0. Зачем вообще это знать

Три практических повода:

1. **Перенести накопленные правила на новую машину.** За полгода работы с
   ассистентом у вас в памяти оседают «не называй номер строки на глаз»,
   «русский язык для документации», «сначала анализ, потом план, потом
   подтверждение» — перенести их простым копированием папки, а не
   пересказывать заново.
2. **Понять, почему ассистент в начале сессии ведёт себя «как будто знает
   проект».** Никакой магии: он прочитал `MEMORY.md` и подгрузил 3–10 строк
   с правилами.
3. **Самому положить правило, если ассистент не догадался.** Формат файлов
   открытый — это просто markdown с frontmatter.

## 1. Где физически лежит память

Вся память — под `~/.qwen/`. Два корня:

```
~/.qwen/
├── memories/                          ← USER-память (кросс-проектная)
│   ├── MEMORY.md                      ← индекс, загружается в каждую сессию
│   ├── user/                          ← кто вы, ваш уровень, роль
│   ├── feedback/                      ← правила поведения «как делать»
│   ├── project/                       ← (обычно пусто в user-памяти)
│   └── reference/                     ← внешние ресурсы
│
└── projects/                          ← PROJECT-память (по проекту на папку)
    └── <slug-рабочей-директории>/
        └── memory/
            ├── MEMORY.md              ← свой индекс
            ├── user/  feedback/  project/  reference/
```

`<slug>` в пути — это автоматически сгенерированное имя из рабочей директории,
например `-home-max-0-0-26-new-one-my-fast-react-case`. Когда вы запускаете
Qwen Code в другом репозитории — там будет **своя** project-память, и
ассистент не полезет в чужую.

### Что в каком каталоге

| Каталог | Что туда класть | Пример |
|---|---|---|
| `user/` | Профиль пользователя: роль, опыт, что знает, что нет | «Уверенно оперирует SPA, history-mode routing, fetch credentials» |
| `feedback/` | Правила «как делать» и «как не делать» — по сути корректировки поведения | «Перед ссылкой на строку N — `awk` её, не вспоминай» |
| `project/` (user) | Почти всегда пусто: проектные факты лучше класть в project-память проекта | — |
| `reference/` | Внешние ресурсы: Linear-доски, Grafana-дашборды, корпоративные вики | «Баги пайплайна в Linear-проекте INGEST» |

В **project-памяти** (внутри `projects/<slug>/memory/`):

| Каталог | Что туда класть |
|---|---|
| `project/` | Факты о проекте: baseline, архитектурные решения, текущая инициатива, кто что делает |
| `feedback/` | Правила, специфичные для этого проекта (например, «в этом репо не запускать pytest — нет тестов») |
| `user/` | Если роль пользователя разная в разных проектах — редкий случай |
| `reference/` | Ссылки на конкретные файлы/доски/документацию этого проекта |

Главное разделение: **user-память кочует с вами между проектами, project-память
привязана к одному репозиторию**. Если правило «русский язык для документации»
должно работать везде — оно в `~/.qwen/memories/feedback/`. Если факт «baseline
routes == 42 в ветке auth_refactor» — в `projects/<slug>/memory/project/`.

## 2. Формат одного файла памяти

Один факт/правило = один файл. Не «пакет правил» в одном файле, не «одна
запись в большой index.md» — по файлу на запись, чтобы можно было удалить
одно правило, не трогая остальные.

Шаблон:

```markdown
---
name: Короткое название правила
description: Однострочный хук — по нему ассистент решает, релевантно ли правило
type: user | feedback | project | reference
---

Тело правила. Для feedback и project — структура такая:
первой строкой **само правило/факт**, затем **Why:** (обоснование — почему
так, какой случай к этому привёл), затем **How to apply:** (когда и как
применять, триггеры).
```

Имена файлов — kebab-case, говорящие: `verify-line-numbers.md`,
`russian-docs.md`, `naming-conventions.md`, `workflow-analysis-plan-approval.md`.
Не нумеровать префиксом (`01-…`, `02-…`) — это не гайды, записи в памяти.

### Пример: правило «не называй номер строки на глаз»

`~/.qwen/memories/feedback/verify-line-numbers.md`:

```markdown
---
name: Проверять номера строк перед публикацией
description: Никогда не называть номер строки по памяти — перед ссылкой
  на «строку N» обязательно прогнать awk/sed/grep и сверить
type: feedback
---

Если в ответе упоминается конкретный номер строки в файле — этот номер нужно
проверить инструментом (awk/sed/grep), а не вспоминать или отсчитывать на глаз.
Если пользователь сам даёт номер строки — сначала сверить с файлом, и только
потом отвечать по существу.

**Why:** 2026-09-05 пользователь указал на предупреждение IDE в `helpers_blog.py:40`.
Я открыл файл, но при формулировке вопроса назвал строкой 40 другую функцию.
Пользователь поймал расхождение мгновенно — у него в IDE номер строки это якорь.

**How to apply:**
- Если собираюсь написать «строка N в файле X» — сначала `awk 'NR==N' X`.
- Если пользователь даёт номер строки как якорь — сначала сверить, потом
  отвечать по существу. Не строить ask_user_question, пока не проверено.
- Если номер и цитата расходятся — не спорить, а сверить и честно сказать.
```

### Пример: проектный факт

`projects/<slug>/memory/project/baseline-routes-42.md`:

```markdown
---
name: Baseline route count for main_app is 42
description: Фактическое значение len(main_app.routes) в этом проекте — 42
type: project
---

`cd fastapi-application && ../.venv/bin/python -c "from main import main_app;
print(len(main_app.routes))"` → **42** на ветке `auth_refactor`.

**Why:** AGENTS.md пишет «41», но эмпирический baseline после 014-remove-dead-
jinja-routes — 42. Спека задания 015 в REQUIREMENTS.md зафиксировала 41, пришлось
править ожидания в чекпоинте.

**How to apply:** В новых заданиях по backend писать критерий успеха как
`routes == 42`. Если в AGENTS.md встретишь 41 — это устаревшее значение.
```

## 3. Файл MEMORY.md — индекс

В каждой папке `memory/` (user и project) лежит свой `MEMORY.md`. Это
**автоматически загружаемый в контекст ассистента** индекс — каждая запись
там это одна строка-ссылка на файл:

```markdown
- [Проверять номера строк перед публикацией](feedback/verify-line-numbers.md) — Никогда не называть номер строки по памяти — перед ссылкой на «строку…
- [Русский язык для документации](feedback/language-russian.md) — Пользователь общается по-русски и хочет русскоязычную документацию (в т.ч. рядом с…
```

Структура:
- одна запись на строку, не больше 150 символов;
- формат: `- [Название](тип/имя-файла.md) — однострочный хук`;
- без frontmatter, без содержимого правил — только указатели;
- `MEMORY.md` **обрезается** на ~200 строках, поэтому записи должны быть
  короткими хуками, а не дублированием тела файла.

Правило: **содержимое правил — в файлах, в `MEMORY.md` — только ссылки**.
Если ассистент в начале сессии должен подгрузить полное правило — он
читает файл по ссылке.

## 4. Что в память НЕ класть

Память — для **выводов и правил**, не для всего подряд. Плохие кандидаты
(часто всплывают в разговорах, но в память идти не должны):

| Не класть | Почему | Откуда брать вместо этого |
|---|---|---|
| Снапшоты структуры проекта («в папке X лежит Y») | Через неделю устареет | `ls`, `tree`, графовый индекс |
| Сводки недавних изменений («вчера перенесли helpers») | Через месяц станет шумом | `git log`, `git diff` |
| Решения конкретных багов («починить 500 на /foo — добавить None-check») | Фикс уже в коде, забывать не надо | `git blame`, `git log -p` |
| Имена инструментов и их параметры | У инструментов есть актуальные схемы | tool-декларации в самой сессии |
| То, что уже в QWEN.md / AGENTS.md / README.md | Дублирование, которое расходится | Эти файлы сами загружаются |
| Текущее состояние задачи («сейчас делаем X») | Быстро устаревает | `tasks/current/REQUIREMENTS.md` |

Хороший тест: если правило останется полезным **через год в другом проекте**
и **без контекста текущего разговора** — класть. Если понятно только из
этого разговора — не класть.

## 5. Как перенести память на другой компьютер

Три варианта, в порядке убывания простоты:

### Вариант 1: tar + копирование (быстро, без истории)

На текущей машине:

```bash
# целиком: и user, и все project
tar -czf memories.tar.gz -C /home/max .qwen/memories .qwen/projects

# или только user-память (project-память всё равно привязана к путям)
tar -czf user-memories.tar.gz -C /home/max/.qwen memories
```

На новой машине:

```bash
# полная копия
tar -xzf memories.tar.gz -C /home/max/

# или только user
tar -xzf user-memories.tar.gz -C /home/max/.qwen/
```

Минус: нет истории изменений, плохое правило придётся вычищать вручную.

### Вариант 2: приватный git-репозиторий (с историей)

Один раз:

```bash
cd /home/max/.qwen
git init
git add memories/ projects/
git commit -m "memory snapshot"
git remote add origin git@github.com:<user>/qwen-memory.git
git push -u origin main
```

На новой машине:

```bash
cd /home/max/.qwen
git clone git@github.com:<user>/qwen-memory.git temp
mv temp/memories .
mv temp/projects .
rm -rf temp
```

Плюс: история, можно `git revert` плохое правило, можно держать на разных
машинах синхронизированно через `git pull`.

Минус: `projects/<slug>/` — это пути, привязанные к машине. На новом компе
slug может быть тот же (если путь совпадает) или другой. Проще держать в
git **только** `memories/`, а `projects/` переносить отдельно под конкретный
slug новой машины.

### Вариант 3: точечное копирование (одно правило)

Если нужно перенести ровно одно правило:

```bash
# на текущей
cat ~/.qwen/memories/feedback/verify-line-numbers.md

# скопировать вывод, создать файл на новой
mkdir -p ~/.qwen/memories/feedback
# вставить содержимое в verify-line-numbers.md
# добавить строку в ~/.qwen/memories/MEMORY.md
```

## 6. Как самому добавить запись в память

### Через ассистента (рекомендуется)

Скажите в чате: «запомни: <правило>». Ассистент сам:

1. Определит тип (user / feedback / project / reference) по содержанию.
2. Выберет каталог (user-память vs project-память) по тому, должно ли правило
   переноситься между проектами.
3. Напишет файл в правильном формате.
4. Добавит строку в `MEMORY.md`.

Если не уверены в формулировке — попросите «сохрани как feedback» явно.

### Вручную

```bash
# выбрать каталог
mkdir -p ~/.qwen/memories/feedback

# создать файл с frontmatter
$EDITOR ~/.qwen/memories/feedback/my-new-rule.md
```

```markdown
---
name: Говорящие имена в логах
description: В логах не использовать сокращения tst/usr/evt — полные слова
type: feedback
---

В log-сообщениях писать полные слова: `test` вместо `tst`, `user` вместо
`usr`, `event` вместо `evt`. Сокращения в логах — антипаттерн, мешают
grep-у и oncall-инженеру в 3 часа ночи.

**Why:** Случай 2026-09-12: oncall искал `User not found` в логах, не нашёл —
оказалось, в коде писали `usr not found`. Потеряли 40 минут.

**How to apply:** При ревью любого logF.info/logF.warning блока. Если видишь
аббревиатуру — попросить заменить.
```

```bash
# добавить в индекс
echo "- [Говорящие имена в логах](feedback/my-new-rule.md) — В log-сообщениях писать полные слова, не сокращать" \
  >> ~/.qwen/memories/MEMORY.md
```

Готово. В следующей сессии ассистент прочитает `MEMORY.md`, увидит ссылку,
при необходимости подгрузит файл.

## 7. Как удалить или исправить запись

- **Удалить правило:** `rm ~/.qwen/memories/feedback/имя.md` + убрать строку
  из `MEMORY.md`. Правило перестаёт действовать сразу.
- **Исправить правило:** `edit`-нуть файл. Правая колонка `description` в
  frontmatter — это хук, по которому ассистент решает, релевантно ли правило.
  Если правило стало шире/уже — поправить и `description`, иначе ассистент
  может не применить его в нужном контексте.
- **Устаревшее правило:** если правило больше не соответствует тому, как
  вы работаете — лучше удалить, чем держать «на всякий случай». Мусор в
  памяти хуже, чем её отсутствие.

## 8. Что память НЕ покрывает

Чтобы не было ложных ожиданий:

- **История чатов не сохраняется.** Память — это выводы, не диалоги. Если
  завтра в новой сессии ассистент вдруг «вспомнит» содержание вчерашнего
  разговора — это не из памяти, а из контекста текущей сессии, который
  пропадёт при перезапуске.
- **Снапшоты git/кода не хранятся в памяти.** Ассистент читает `git log`,
  `git diff`, `git blame` вживую. В памяти — только интерпретация, не
  сами данные.
- **Секреты не должны попадать в память.** Если в разговоре мелькнул
  API-ключ или пароль — ассистент не запишет его в файл памяти. Если
  случайно записалось — удалите файл и перевыпустите секрет.
- **Размер `MEMORY.md` ограничен ~200 строками.** Если правил слишком
  много — старые автоматически отсекаются. Держите записи короткими, а
  файлы — сфокусированными.

## 9. Мини-чеклист: что делать после прочтения

- [ ] Посмотреть текущую память: `ls -R ~/.qwen/memories/ ~/.qwen/projects/`
- [ ] Прочитать `~/.qwen/memories/MEMORY.md` — увидеть, какие правила
      ассистент сейчас применяет
- [ ] Решить, какие правила **должны быть** и **отсутствуют** — добавить
      через «запомни» в чате
- [ ] Если планируете работать на нескольких машинах — завести приватный
      git-репо с `memories/`
- [ ] Удалить правила, которые ассистент применяет не к месту — они мешают
      больше, чем помогают
