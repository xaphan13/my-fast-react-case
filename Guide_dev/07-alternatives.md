# 07. Альтернативные подходы: что ещё бывает и когда это брать

> Цикл «FastAPI + React». Предыдущая: [06. Связка и деплой](06-integration-deploy.md) · Следующая: [08. Чеклист](08-checklist-new-project.md)

SPA на Vite — не единственный способ. Ниже пять подходов, все они реальны и
применяются; в этом проекте выбран способ A.

## Способ A. SPA-статика на FastAPI (этот проект)

```
Разработка:   Vite :5173 (HMR) ──proxy──▶ FastAPI :8000
Эксплуатация: npm run build → dist/ ◀── раздаёт FastAPI (mount + catch-all)
```

- **Плюсы:** один сервер и порт; нет CORS; нулевая инфраструктура вокруг
  фронтенда; API переиспользуется любым клиентом.
- **Минусы:** пустой `index.html` — слабое SEO; правки фронтенда требуют
  пересборки; для разработки нужен второй процесс.
- **Берите если:** личный/внутренний сервис, дашборд, JSON-first сайт, блог с
  API-доступом.

## Способ B. Раздельные домены: CDN/Nginx + API

```
Браузер ──▶ https://app.example.com  (Nginx/Vercel/Cloudflare Pages — dist/)
        ──▶ https://api.example.com  (FastAPI — только JSON)
```

- **Плюсы:** независимое масштабирование; CDN для статики; API как продукт для
  мобильных приложений и партнёров; фронтенд-команда деплоится сама.
- **Минусы:** **CORS обязателен** (`CORSMiddleware`, `allow_origins`,
  `allow_credentials=True`); cookie через домены — `SameSite=None; Secure` и
  общий родительский домен; два деплоя и два сертификата.
- **Берите если:** публичный продукт, отдельные команды, мобильные клиенты.

## Способ C. SSR-фреймворк (Next.js / Remix) + FastAPI

```
Браузер ──▶ Next.js (Node-сервер рендерит HTML) ──fetch──▶ FastAPI API
```

React-компоненты исполняются **на сервере**: в браузер приходит HTML уже с
контентом, hydration достраивает интерактив.

- **Плюсы:** SEO (контент в HTML сразу), быстрая первая отрисовка, метатеги для
  соцсетей.
- **Минусы:** Node — обязателен в *рантайме* (не только в сборке); двойной
  рендер и hydration-состояние; заметно выше сложность эксплуатации.
- **Берите если:** SEO-критичный контентный продукт (маркетплейс, медиа),
  социальные превью обязательны.
- **Замечание:** Python-альтернатива «SSR для FastAPI» — шаблоны Jinja2 +
  частичный гидрат; полноценного Next.js-эквивалента в экосистеме Python нет.

## Способ D. Серверные шаблоны: Jinja2 (+ htmx / Alpine.js)

```
Браузер ──▶ FastAPI: Jinja2-рендер HTML + точечная интерактивность (htmx)
```

Никакого бандла: сервер отдаёт готовый HTML, «тонкий» клиент, интерактив
добавляется декларативно (htmx превращает атрибуты HTML в AJAX-запросы).

```html
<!-- htmx: кнопка шлёт POST и подменяет фрагмент HTML из ответа -->
<button hx-post="/orders/7/confirm" hx-target="#order-status">Подтвердить</button>
```

- **Плюсы:** минимум движущихся частей; Node не нужен вовсе; SEO из коробки;
  один язык шаблонов и один процесс.
- **Минусы:** богатая интерактивность (drag-and-drop, сложное состояние) даётся
  тяжело; компонентности нет; клиентское состояние размазано по DOM.
- **Берите если:** классический сайт с формами, админки, небольшой интерактив.

## Способ E. Гибрид «островков»: HTML-каркас + React-виджеты

FastAPI (Jinja2) рендерит страницу, а в конкретные места монтируются React-виджеты:

```html
<div id="comments-root"></div>
<script type="module">
  import { createRoot } from 'react-dom/client';
  createRoot(document.getElementById('comments-root')).render(<Comments articleId={7} />);
</script>
```

- **Плюсы:** SEO и скорость серверного HTML + точечная интерактивность без
  SPA-роутинга.
- **Минусы:** два мира в одном проекте; общее состояние между «островками» —
  боль; сборка всё равно нужна.
- **Берите если:** контентный сайт, где интерактив нужен локально (комментарии,
  корзина), а остальное — статьи. Идею в чистом виде реализует Astro (islands).

## Сравнительная таблица

| Критерий | A: SPA на FastAPI | B: раздельные домены | C: Next.js SSR | D: Jinja2 | E: островки |
|---|---|---|---|---|---|
| Node в рантайме | нет | нет | **да** | нет | нет |
| CORS-настройка | не нужна | **обязательна** | не нужна (прокси) | не нужна | не нужна |
| SEO | слабое | слабое | **отличное** | **отличное** | хорошее |
| Деплой-юнитов | 1 | 2 | 2 | 1 | 1 |
| Сложность | низкая | средняя | высокая | низкая | средняя |
| Богатый интерактив | **да** | **да** | **да** | ограничен | точечно |
| Команда | 1–2 | 2+ | 2+ | 1–2 | 1–2 |

## Как выбрать: три вопроса

1. **Кто ищет сайт в Google?** Контент, который должен ранжироваться и
   превьюшиться в соцсетях → C или D/E. Дашборд за логином → A (SEO не нужен).
2. **Один клиент или много?** Только браузер → A. Мобильные приложения,
   партнёры, публичный API → B.
3. **Сколько интерактивности?** Формы и списки → D. Настоящее приложение
   (фильтры, drag-and-drop, офлайн) → A/C.

## Альтернативы внутри выбранного способа

Даже внутри «A: FastAPI + React SPA» есть развилки, о которых стоит знать:

| Развилка | Вариант проекта | Альтернативы |
|---|---|---|
| Клиентское состояние | React Context (`AuthContext`) | Redux Toolkit, Zustand, TanStack Query (серверное состояние + кэш) |
| Стили | Tailwind CSS v4 | CSS-модули, styled-components, vanilla-extract |
| Сборка | Vite | rspack/turbopack (более новые), webpack (легаси) |
| Типы контракта | ручной `types.ts` | генерация из OpenAPI (`openapi-typescript`, `orval`) |
| Валидация на клиенте | нативная HTML5 + сервер 422 | zod с переиспользованием схем |
| Аутентификация | cookie-сессии | JWT (access+refresh), OAuth2-провайдеры |

**Практическое правило:** начинайте с минимума (Context + Tailwind + ручные
типы), а библиотеки добавляйте, когда почувствовали боль, — не наоборот.

## Миграции между способами реальны

Ключ к безболезненности миграции между способами — **контракт**: проектируйте
домен и API независимо от способа рендеринга. Тогда смена подхода (например,
с серверных шаблонов на SPA или обратно) станет заменой одного слоя, а не
переписыванием всего приложения.
